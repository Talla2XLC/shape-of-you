# Привязывать естественное принятие TrainingProgram к последней полной опубликованной версии

## Context

Принятый ADR о сохранении подтверждённой программы одной атомарной командой
закрепил Person-owned `TrainingProgram`, неизменяемые версии, semantic duplicate
no-op, optimistic stale protection и обязательный read-back. Однако
model-facing contract требует «explicit confirmation», не определяя, что
обычные ответы «да», «го», «подходит» или «делаем так» являются достаточным
подтверждением уже показанной полной версии.

Coach поэтому может понимать, что программа составлена, одновременно получать
`no_active_training_program`, продолжать говорить о предложении как о плане и не
вызывать сохранение. Пользователь вынужден повторять программу или знать
внутреннее имя команды. Обратная крайность — считать подтверждением любую
позитивную реакцию — может сохранить не ту версию, ответ на другой вопрос либо
частично обсуждённый вариант.

Backend не получает исходную естественную реплику и не должен интерпретировать
её эвристическим parser. Conversation orchestration уже имеет полную показанную
версию, пользовательский ответ и существующую typed команду, которая повторно
передаёт весь snapshot.

## Decision

1. Полная программа, которую пользователь сам передал вместе с однозначной
   просьбой использовать, сохранить или сделать активной, является достаточной
   authority для немедленного сохранения. Дополнительное подтверждение не
   требуется.
2. Для программы, предложенной Coach, обычное естественное согласие считается
   подтверждением только тогда, когда оно однозначно относится к последней
   полностью опубликованной версии, предложенной для активации. Это не набор
   magic phrases: язык и формулировка могут различаться.
3. Позитивная реакция не подтверждает программу, если между полной публикацией
   и ответом появился другой вариант, частичная правка, сомнение, вопрос или
   unrelated yes/no prompt. В неоднозначном случае Coach сразу задаёт один
   короткий вопрос: «Сохраняю эту программу как активную?»
4. Обсуждение, вопрос, сомнение, альтернатива или частичная правка не являются
   подтверждением. После правки Coach сначала публикует новую полную версию;
   недостающие упражнения, порядок, нагрузки и прогрессия не додумываются.
5. До успешной записи и проверки программа остаётся только `Proposed now`.
   Слова «согласована», «действует», «наш план» и эквиваленты разрешены только
   после совпадающего активного `TrainingProgramVersion` read-back.
6. После однозначного принятия orchestration в том же ходе вызывает существующий
   `save_confirmed_training_program`, затем `get_training_context` и сравнивает
   полный активный snapshot с принятой версией. Пользователь не видит внутренние
   имена tools, поля, статусы или transport details.
7. При stale conflict orchestration перечитывает контекст. Если активный
   snapshot уже совпадает с принятой версией, read-back подтверждает успех. Если
   он отличается, автоматическая перезапись запрещена: Coach сохраняет уже
   известную принятую версию в conversation context и коротко спрашивает,
   заменить ли текущую активную программу, не требуя повторного ввода.
8. При другой ошибке Coach один раз перечитывает состояние. Без совпадающего
   read-back он не заявляет об успехе и предлагает безопасно повторить
   сохранение без повторения всей программы.
9. Новая серверная proposal-сущность или token не создаётся. Conversation
   orchestration владеет только временной связью реплики с предложением;
   PostgreSQL остаётся единственной authority активной программы.

## Considered alternatives

### Подтверждение только специальной командой или формулой

Синтаксически однозначно, но переносит внутренний orchestration contract на
пользователя, создаёт magic phrases и сохраняет наблюдаемый дефект. Отклонено.

### Автоматическое сохранение по любой позитивной реакции

Минимально по трению, но «да» или похвала могут относиться к другому вопросу,
одной части либо более старой версии. Material write становится небезопасным.
Отклонено.

### Контекстная привязка к последней полной опубликованной версии

Использует доступный conversation context, полный typed snapshot, существующую
атомарную запись и обязательный read-back. Устраняет magic phrases, сохраняя
fail-closed boundary для неоднозначных случаев. Выбрано.

### Серверная proposal-сущность или token

Token доказывал бы только то, что некоторый snapshot ранее зарегистрирован, но
не то, к чему относилось естественное «да»: orchestration всё равно выбирает
token. Появились бы prepare/confirm lifecycle, expiry, cancellation,
multi-conversation concurrency, storage, migration и cleanup для объекта,
который ещё не является доменной authority. Отклонено как лишняя сложность.
Вариант следует пересмотреть отдельным ADR только при live evidence сохранения
неправильной версии после усиленного контекстного контракта.

## Consequences

- Естественное однозначное согласие завершает сохранение без повторения
  программы и технических команд.
- Conversation context временно связывает принятие с предложением, но не
  становится вторым источником истины: действующий план существует только
  после PostgreSQL write и совпадающего read-back.
- Existing `TrainingProgram` schema, repository transaction, scopes и HTTP
  lifecycle не меняются; migrations, dependencies, secrets и новые services не
  требуются.
- Model-facing contract остаётся вероятностной внешней orchestration boundary,
  поэтому после release требуется same-conversation canary с естественными и
  неоднозначными фразами.

## Verification

- MCP contract tests фиксируют direct user authority и естественное принятие
  последней полной Coach-версии.
- Отрицательные fixtures охватывают похвалу без принятия, вопрос, сомнение,
  альтернативу, частичную правку, unrelated yes/no и несколько версий.
- Tests требуют последовательность save → `get_training_context` → полное
  сравнение до active/saved claim.
- Failure tests проверяют stale-already-applied, stale-different-active,
  unavailable read и продолжение без повторного ввода программы.
- Existing Training integration tests продолжают доказывать Person ownership,
  immutable versions, atomicity, duplicate no-op и stale rollback.
