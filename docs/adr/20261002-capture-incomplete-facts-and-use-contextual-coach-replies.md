# Принимать неполные факты без выдуманных деталей и отвечать по смыслу разговора

## Context

Оператор сообщил о разговоре, в котором Coach не сохранил тренировку,
объяснял внутренние ограничения и после простых сообщений навязывал указания.
Сообщения «разведения сделал», «дальше тяжко» и разовая замена на Smith
содержат реальные факты, даже если подробностей недостаточно для прогрессии.

Проверка репозитория установила:

- WorkoutSession write требует хотя бы одно упражнение, точный
  exerciseVersionId и хотя бы один измеренный подход каждого упражнения.
  RIR может быть null; диапазон «1–2» нельзя без основания заменять одним числом.
- Repository проверяет существование версии программы и позиции, но не требует
  совпадения всех выполненных упражнений с назначениями. Причина конкретного
  отказа из переписки неизвестна без фактической ошибки запроса.
- WorkoutSession read и PostgreSQL уже поддерживают temporalPrecision =
  local_date с occurredAt = null; интерактивный write требует точный instant.
- Meal domain поддерживает неизвестное количество и nullable nutrients,
  но MCP completeness guard блокирует accepted item без всех четырёх чисел.
- MCP presenters требуют интерпретацию и следующий шаг практически после
  каждого содержательного сообщения. Это соответствует принятому ADR от
  2026-09-02, но конфликтует с желаемым естественным разговором.
- MCP и HTTP validators уже задают multipleOfPrecision = 6. Число 3.3
  соответствует точности 0.001; конкретная ошибка не доказана и не является
  основанием менять numeric invariants или обещать исправление этого сбоя.

Оператор утвердил исправленные ADR и план 2026-10-02 сообщением «го».
Решение принято; реализация и delivery проверяются отдельно.

## Decision

### Сначала сохранить известный факт

Прямой отчёт о выполнении или обычное уточнение разрешает routine capture
без отдельного «сохранить?». Сохранять только сказанное пользователем или
обоснованную явно обозначенную оценку; программа не доказывает выполнение.
Нехватка деталей ограничивает производную аналитику, а не сохранение факта.

Training расширяет существующие WorkoutSession и PerformedExercise, не создавая
новую универсальную сущность, очередь разговоров или отдельный сервис:

- WorkoutSession может подтверждать завершённую тренировку без перечня
  упражнений. Во время выполнения сохраняются только явно выполненные части;
  факт окончания задаётся отдельным completionState = in_progress | completed.
  Старые сессии получают completed: их прежняя семантика — завершённый факт.
- PerformedExercise сохраняет сообщённое имя, даже если каталог не разрешён:
  exerciseId и exerciseVersionId либо оба известны, либо оба null. Отсутствие
  каталожной идентичности не препятствует хранению reported label.
- sets = [] означает «выполнение упражнения подтверждено, подходы неизвестны»,
  а не ноль выполненных подходов. Известные подходы хранятся как сейчас;
  частично известный подход может иметь nullable измерения, но не может быть
  полностью пустым. Текст усилия и исходный диапазон RIR сохраняются в note,
  числовой RIR остаётся null, если точного значения нет.
- Неизвестный loadBasis остаётся null. «60 кг блинов» сохраняется как
  external_weight без добавления неизвестной массы грифа или механизма Smith.
- При известном только дне использовать local_date, не выдумывать время старта.
  createdAt не является occurredAt. Неоднозначную дату уточнять только когда
  её нельзя установить из доступного контекста и Person timezone.
- Последующие подробности создают append-only full-replacement correction
  одной однозначно определённой сессии, сохраняя остальные данные.
  Capture/correction выполняются под Person lock с проверкой текущего
  predecessor и идемпотентностью. Повтор не создаёт вторую тренировку;
  конфликт требует свежего чтения, а не автоматического затирания.

### Фактическая замена и согласованное изменение программы

Smith сохраняется под фактическим именем, не подменяется свободной штангой.
Известную версию упражнения разрешать только точным доступным match;
при отсутствии или неоднозначности хранить reported label без каталожной
идентичности. Последующее разрешение является correction; автоматически
создавать публичный каталог запрещено.

Сам отчёт о Smith подтверждает выполненное упражнение, но не выражает решения
обо всех следующих тренировках. После сохранения Coach может естественно
спросить: «Оставляем Smith только на сегодня или заменяем им присед в программе?».
Это полезное уточнение намерения, а не разрешение на сохранение уже выполненного.
Не повторять вопрос, если пользователь уже сообщил, что замена разовая или
постоянная. Прямое «замени в программе» либо однозначный ответ на предложение
разрешает согласованную замену через существующий TrainingProgram lifecycle.

Coach показывает, какое назначение меняется, и использует существующий
save_confirmed_training_program с immutable successor и optimistic lock.
При явно указанном исходном назначении и целевом упражнении краткого запроса
замены достаточно: внутренний полный snapshot собирается из прочитанной
программы, пользователь не должен повторять или заново подтверждать всю её
неизменённую часть. Если исходное назначение неоднозначно, уточнить только его.
Не переносить рабочий вес, loadBasis или progression между разными механизмами
без обоснования: предложить подходящее новое назначение, а значимые неуказанные
параметры согласовать вместе с заменой. Незатронутые prescriptions и cadence
сохраняются. Matching active read-back предшествует заявлению об изменении.
При stale конфликте перечитать программу и не затирать другое изменение.
Постоянная замена не переписывает старые тренировки и не переносит progression
evidence свободной штанги на Smith.

Связь с A/B означает подтверждённую позицию программы, а не полное соблюдение
назначений. Только явно завершённая сессия с надёжной A/B identity продвигает
cadence. In-progress запись не закрывает день или недельную квоту. Personal
records и progression используют только подходящие измеренные данные с
разрешённой exercise identity и совместимым loadBasis; неизвестное не ноль.
Разовая замена не является evidence для повышения веса другого упражнения.
Автоматическое связывание с external activity по времени запрещено для
local_date; существующие явные и доказанные связи сохраняются.

### Еда и разговор

Обычное отсутствие точных граммов или нутриентов не означает невозможность
оценки. Сохранить привычное поведение: Coach сам оценивает количество по фото
или описанию, использует средние значения для соответствующего продукта и
способа приготовления, рассчитывает nutrients и сообщает пользователю
«примерно». Не требовать весов, рецепта или точных БЖУ ради обычной записи.
Estimated evidence отличается от измеренного факта; средняя оценка не является
выдуманным результатом тренировки и не требует того же запрета на inference.

Unknown/described amount и nullable nutrients остаются исключением: только
когда нет достаточной основы для разумной оценки, а не при каждом пропущенном
поле. MCP разрешает эти уже существующие domain states, чтобы отсутствие
разумной оценки не уничтожало известный факт. Daily totals сохраняют текущую
partial/null семантику. Исправление «это кукуруза» меняет выбранный item и
пересчитывает затронутую оценку, сохраняя остальные items; не запрашивать
дополнительное подтверждение понятной корректировки.

Reply policy доставляется через существующий per-result механизм:

- routine capture/correction допускает простое короткое подтверждение;
  наблюдение, совет и вопрос добавляются только если полезны в этом контексте;
- запрос совета и полный Daily Coach ответ сохраняют предметный ответ и
  существующие границы verified decision evidence;
- ошибка записи объясняется кратко и честно; нельзя заявлять сохранение до
  matching read-back, обещать последующее фоновое сохранение или выдавать
  предположение о причине за установленный факт;
- обычный ответ не содержит tool/schema/storage vocabulary. На прямой
  технический вопрос пользователя допустимо понятное объяснение подтверждённой
  причины и неопределённости без секретов и сырых payloads;
- вопрос нужен при существенной неоднозначности цели или коррекции, а не для
  заполнения каждого неизвестного поля. Проактивность остаётся возможной,
  обязательное завершение каждого ответа рекомендацией отменяется.

### Пересмотр прежней политики

Это решение заменяет ADR от 2026-09-02 в части обязательного совета и запрета
объяснять подтверждённую причину на прямой технический вопрос. Принятый
per-result механизм доставки, typed facts, verified write и OAuth boundary
сохраняются. Правила полной новой программы из ADR от 2026-09-22 продолжают
действовать; однозначная согласованная замена отдельного назначения является
описанным здесь расширением, а не разрешением на остальные изменения.

### Совместимость и доставка

Существующие MCP input contracts не сужаются и не получают новых required
fields. Расширение Meal capture выполняется аддитивно. Новый Workout contract
меняет допустимую семантику результата: nullable exercise identity и completion
нельзя незаметно подставить старым strict consumers. Ввести согласованный V2
capture/correction/read набор и обновить внутренние consumers; старые tools
сохранить для прежнего полного формата. Если legacy read встречает факт,
непредставимый в его контракте, вернуть явную ошибку несовместимости вместо
скрытия факта, fabricated ids или ложного пустого списка.

Per-result reply policy обновляет речь уже открытых чатов после следующего
вызова. Новые возможности Workout V2 требуют публикации каталога и проверки
доступности клиенту; не обещать их появление в cached conversation без проверки.
Сохранить OAuth scopes и Person ownership. Миграция расширяет Training-owned
таблицы и не переписывает исторические значения. Deploy, migration execution,
connector refresh и live writes требуют отдельных operational approvals.

## Considered alternatives

| Вариант | Преимущество | Недостаток |
| --- | --- | --- |
| Только смягчить prompt | Быстро, без схемы | «Сделал» по-прежнему нельзя надёжно сохранить |
| Требовать полный отчёт | Простой строгий write | Перекладывает структуру на пользователя и теряет факты |
| Подставлять плановые sets и RIR | Проходит текущий validator | Создаёт ложную историю и неверную прогрессию |
| Generic note или отдельный chat inbox | Принимает любой текст | Второй источник фактов, повторная обработка и сложнее коррекции |
| Расширить существующие domain facts | Одна authority, честное unknown | Нужны migration, V2 contracts и изменения consumers |

Выбран последний вариант. Не создавать свой chat runtime ради контроля речи.

## Consequences

Человек может сообщать результаты постепенно, без обязательной анкеты.
Разговорная неполнота становится нормальным состоянием evidence. Цена решения:
обновление Training schema, serializers, queries и тестов; временная
совместимость старых tools ограничена полным прежним форматом.

API управляет instructions и фактами, но внешний клиент формирует финальный
текст. Тесты presenters не доказывают буквальное поведение живого агента.
После согласованной доставки необходим conversational canary.

## Verification

- Контрактные и PostgreSQL тесты: completion, пустые exercises/sets, частичные
  измерения, unresolved exercise identity, null loadBasis, local_date,
  correction lineage, конкурентные изменения и idempotent retries.
- Regression сценарий переписки: известные четыре упражнения сохраняются;
  разведения подтверждены без выдуманных sets; Smith не превращается в штангу;
  reported диапазон RIR не усредняется; известная только дата остаётся датой.
- Замена программы: только сегодня, подтверждённая постоянная замена, прямой
  запрос пользователя, неоднозначное исходное назначение и stale конфликт;
  неизменённая часть программы сохраняется, старые сессии не переписываются,
  нет автоматического переноса weight/progression между механизмами.
- Cadence, progression, personal records, linking, daily facts и timeline:
  in_progress не закрывает тренировку; unknown не становится нулём или
  measured evidence; completed correction считается ровно один раз.
- Meal по фото и описанию без граммов получает обоснованные средние estimates
  и естественное «примерно», не массовые null и не обязательное уточнение.
  Unknown/described проверяются для отсутствия основы оценки; correction
  кукурузы пересчитывает только затронутые данные. Известное 3.3 проходит
  validators без изменения значения; incomplete nutrients не дают ложных totals.
- Frozen legacy schemas, V2 publication, честная несовместимость legacy read;
  presentation fixtures допускают acknowledgement-only и не требуют совета.
- Clean/prefix migration checks и статическая проверка PostgreSQL identifiers
  на предел 63 UTF-8 bytes; independent Quality и Architecture Review.
- Canonical documentation validator; staging smoke и conversational canary
  только в отдельно разрешённом environment и scope.
