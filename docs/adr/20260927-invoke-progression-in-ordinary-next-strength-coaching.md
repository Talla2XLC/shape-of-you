# Вызывать прогрессию при обычном обсуждении следующей силовой тренировки

## Context

TASK-0135 уже предоставляет read-only `get_training_progression`: Training
рассчитывает решение по подробным `WorkoutSession`, а Coaching проверяет
текущий `Daily Assessment` и точную активную программу. Инструкция Coach
вызывает инструмент преимущественно при прямом вопросе о прогрессии, поэтому
обычный разговор о следующей силовой тренировке может пропустить полезное
объяснение веса и повторений.

## Decision

Правила полномочий и orchestration нового Coach заменены
[ADR базы знаний](20261009-let-coach-propose-working-weight-from-history.md).
Исторические snapshots, compatibility commands и технические гарантии хранения
сохраняют прежний смысл; supersession не переписывает существующие данные.

1. Расширить только инструкцию выбора MCP-инструмента. При обычном обсуждении
   выполнения следующей силовой тренировки, её рабочих весов, повторений или
   подходов Coach сначала читает текущий `get_daily_assessment`, затем
   `get_training_context`. Если оценка `ready`, действие
   `follow_active_program`, а next step однозначно указывает на силовую
   тренировку точной активной версии, Coach вызывает
   `get_training_progression` один раз в этом ходе разговора.
2. При ограничении восстановления, отсутствии или неясности активного шага,
   завершённой тренировке или неделе Coach не вызывает прогрессию. Она также
   не нужна для записи факта, общих вопросов, питания и самостоятельного
   обсуждения восстановления. Прямой вопрос о прогрессии не отменяет
   ограничения `Daily Assessment` и не вызывает лишний read.
3. `Daily Assessment` остаётся единственным решением о сегодняшнем действии.
   Прогрессия лишь поясняет параметры разрешённого силового шага и не добавляет
   тренировку, интенсивность или действие, которых оценка не вернула.
   Неуспешные или несовпадающие reads закрывают путь к предложению прибавки.
4. Текущая оценка не гарантирует готовность к тренировке в будущем. Coach
   представляет совет для будущей тренировки условно и предлагает заново
   проверить восстановление в её день. Только `WorkoutSession` даёт фактические
   sets; Garmin summary не даёт выполненные weight, reps или RIR.
5. Совет остаётся read-only и не меняет active `TrainingProgram`. Новые
   сущности, схема данных, маршрутизатор, клиент и сервис не добавляются.

## Considered alternatives

### Оставить вызов только для прямого вопроса

Минимум запросов, но обычный разговор о следующей силовой тренировке не
получит уже доступное объяснение. Не выполняет цель задачи.

### Добавить серверный маршрутизатор намерений и автоматический prefetch

Он мог бы детерминированно проверять выбор инструмента, но потребовал бы новый
слой управления разговором и его интеграцию с внешним MCP-клиентом.
Сложность несоразмерна изменению; отклонено.

### Уточнить MCP-инструкцию с проверяемыми условиями вызова

Использует существующие authority и read-only инструмент без нового
владельца решения. Выбрано. Серверные тесты проверяют опубликованный контракт
и gate инструмента; фактический выбор внешней модели требует отдельной
поведенческой проверки клиента.

## Consequences

- Coach чаще объясняет `hold`, `add_reps`, `add_weight` и недостаточность
  данных в уместном разговоре о следующей силовой тренировке.
- При подходящем разговоре появляется один дополнительный read-only вызов;
  ограниченные и посторонние сценарии его пропускают.
- Изменение инструкции само по себе не даёт детерминированной гарантии выбора
  инструмента внешней моделью.

## Verification

- MCP contract tests для условий необходимых и лишних вызовов, порядка чтений,
  Recovery precedence, будущей даты, Garmin и запрета изменения программы.
- Существующие unit tests `DailyAssessmentService` подтверждают server-side
  fail-closed gate; проверить MCP response и связанные регрессии.
- `lint`, `typecheck`, API unit tests, docs validation, независимый Quality
  Review и Architecture Review.
