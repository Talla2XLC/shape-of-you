# Импортировать историю Intervals.icu только по запросу пользователя

## Context

Текущая синхронизация Garmin через Intervals.icu повторно читает ограниченное
скользящее окно. Это подходит для актуальных данных и поздних исправлений, но не
загружает всю доступную историю пользователя.

Полный исторический импорт может потребовать много запросов и времени. Запускать
его сразу после OAuth без отдельного намерения пользователя нельзя: подключение
аккаунта и импорт многолетней истории — разные действия с разной стоимостью и
ожиданиями.

На странице Connections также смешаны три разных действия: обычная
синхронизация, disconnect и необратимое удаление импортированных данных.
Текущая надпись `Confirm with passkey and delete imported data` описывает
технический шаг вместо результата и выглядит как основное действие.

## Decision

Обычное подключение и повторная синхронизация продолжают работать только со
скользящим актуальным окном. OAuth callback не запускает полный исторический
импорт.

Полная доступная история запускается отдельным аутентифицированным действием
`Import historical data…`. Перед запуском интерфейс явно сообщает, что будут
импортированы доступные Intervals.icu wellness и activities за прошлые периоды,
и просит подтверждение. Повторное нажатие во время активного процесса не создаёт
вторую работу.

Исторический импорт выполняется существующим in-process worker внутри
`apps/api`. Новый микросервис и новая очередь заданий не создаются. Состояние
принадлежит конкретной `IntegrationConnection` и сохраняется долговременно:
статус, курсор самой ранней обработанной даты, время запроса и завершения,
следующая попытка и ограниченный безопасный failure code.

Worker сначала сохраняет приоритет обычной актуальной синхронизации, а затем,
только при наличии пользовательского запроса, обрабатывает не более одного
ограниченного исторического окна за claim. Окна идут назад от границы текущего
скользящего периода, имеют размер не более 180 дней и продолжаются до
`2000-01-01`. Паузы, rate limiting и повторные попытки не должны блокировать
обычные API reads или переводить само подключение в disconnected.

Исторические данные проходят тот же provider adapter, schema validation,
нормализацию, inbox и typed Recovery/Training import, что и актуальные данные.
Отдельная raw JSON модель не создаётся. Совпадающие provider identity и checksum
являются no-op; исправленные provider records используют существующую модель
correction/supersession.

Безопасная browser projection отдельно показывает состояние истории:
`not_requested`, `running`, `completed` или `failed`, достигнутую дату и время
последней попытки/завершения. Provider response, tokens и другие чувствительные
детали в projection и logs не попадают. Временная ошибка истории сохраняет уже
импортированные данные и допускает безопасное продолжение с курсора.

Disconnect прекращает новый актуальный и исторический импорт, но сохраняет уже
полученные данные. Удаление импортированных данных остаётся отдельным действием
и использует существующий fresh-passkey и fail-closed journal lifecycle.

На Connections используются три ясно разделённых элемента управления:

- `Import historical data…` — компактная secondary action;
- `Disconnect` — прекращает последующую синхронизацию без удаления;
- `Delete imported data…` — компактная destructive action в отдельной
  `Danger zone`.

Возле удаления показывается текст: `Permanently deletes data imported through
this connection. Passkey confirmation is required.` Passkey не упоминается в
названии кнопки, потому что это способ подтверждения, а не результат действия.
Destructive action не растягивается на всю ширину карточки даже при узком
viewport.

## Considered alternatives

- **Автоматически импортировать всю историю после OAuth.** Отклонено: соединяет
  два разных пользовательских намерения и без явного запроса создаёт дорогую
  фоновую работу.
- **Просить пользователя выбрать начальную дату.** Сокращает число запросов, но
  усложняет основной сценарий и не отвечает простому намерению «импортировать
  доступную историю». Может быть добавлено позже отдельным решением.
- **Выполнять импорт одной длинной HTTP-операцией.** Отклонено из-за timeout,
  rate limits и невозможности надёжно продолжить процесс после рестарта.
- **Создать отдельный сервис или универсальную job queue.** Отклонено как
  преждевременная deployable boundary для одного ограниченного provider flow.
- **Операторский скрипт.** Не является пользовательской функцией и не даёт
  человеку понятного состояния и повторяемого управления.

## Consequences

- Подключение остаётся быстрым и не запускает неожиданную загрузку истории.
- Пользователь сам инициирует потенциально длительный импорт и видит его
  состояние.
- Потребуется миграция `integration_connections` и расширение browser API
  contract; создание migration входит в реализацию, а её применение остаётся
  отдельным operator gate.
- Полный проход до нижней границы может занять продолжительное время из-за
  provider rate limits. `Completed` означает, что все запланированные окна были
  безопасно обработаны, а не что Intervals.icu гарантировал данные на каждую
  дату или каждую метрику.
- Новые credentials, secrets и ручная конфигурация VM не нужны.

## Verification

- Contract и controller tests доказывают, что OAuth не запускает историю, а
  явный POST запускает одну durable работу только для активного Person
  connection.
- Repository и PostgreSQL integration tests проверяют сохранение курсора,
  продолжение после рестарта, допустимые переходы состояния и ограничения имён
  PostgreSQL в 63 UTF-8 bytes.
- Worker tests проверяют порядок актуальной синхронизации и одного
  исторического окна, retry/backoff, disconnect и независимость ошибок истории
  от connection lifecycle.
- Fake provider tests проверяют диапазоны, duplicate no-op и correction для
  wellness и activities без настоящего Intervals.icu аккаунта.
- Web tests проверяют тексты, подтверждение запуска, состояние прогресса,
  разделение `Disconnect` и `Delete imported data…`, fresh-passkey redirect и
  компактное отображение destructive action на узком viewport.
- Перед handoff выполняются targeted tests, полные доступные проверки API/Web,
  `node scripts/validate-docs.mjs`, `git diff --check` и `4dt-board validate`.
