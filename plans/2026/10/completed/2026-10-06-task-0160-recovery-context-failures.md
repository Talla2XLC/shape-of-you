# TASK-0160 — отказы дневного Recovery-контекста

## Статус и разрешение

Оператор утвердил этот план отдельным сообщением «го» после read-only
диагностики staging на `talking-to-ai`. Реализация выполнена в primary tree
и принята независимой Quality: `task-0160-quality-acceptance-20261006`.
Этот план не разрешает commit, push, deploy, миграции или изменение фактов.

## Проверенные факты

- 6 октября оба MCP чтения `get_current_recovery_context` и
  `get_daily_decision_context` вернули общий отказ. Отдельные Recovery и
  Training reads работали. Исходная причина исключения не сохранена.
- Позднее оба MCP чтения заработали. На staging штатные методы preferences,
  observations, delivery и current context прошли в отдельной READ ONLY
  сессии через подключение API. Транзакции завершены, соединение закрыто.
- Формат Person-local даты, валидность timezone, наличие нужных столбцов и
  SELECT-права API проверены. Это исключает только проверенные постоянные
  несоответствия, а не все возможные временные ошибки.
- Локальные 21 unit и 30 isolated PostgreSQL integration tests проходят.
  MCP fixtures подставляют результаты композиции и не воспроизводят
  проверенный временный отказ. Успешные reads сейчас не объясняют прошлый отказ.
- Общий catch в MCP adapter подавляет причину этих read failures без
  диагностического ID и безопасной записи ошибки. Поэтому конкретный
  таймаут, перегрузка, гонка или отказ провайдера не доказаны.

Персональные значения, идентификаторы и исходные логи в план не включаются.
Подробная операционная проверка хранится в managed timeline TASK-0160.

## Архитектурная граница

Authority остаётся в accepted
[ADR дневного решения](../../../../docs/adr/20260928-let-coach-decide-from-verified-daily-facts.md),
[ADR частоты тренировок](../../../../docs/adr/20261004-use-rolling-training-frequency-as-coach-guidance.md)
и действующей MCP границе. Новых сущностей, таблиц, миграций, сервисов,
разрешений на тренировку или алгоритмов готовности нет. Полный отказ чтения
отличается от успешного контекста с отсутствующим отдельным показателем.

## Альтернативы

1. Безопасная диагностика двух составных reads и уточнение действующих
   инструкций Coach — рекомендуемый узкий объём. Позволяет расследовать
   следующий отказ и не выдавать очередь тренировок за доказательство готовности.
   Не восстанавливает исключение прошлой попытки и не обещает устранить
   неустановленную runtime-причину.
2. Только уточнение инструкций Coach — меньше изменений, но следующий отказ
   снова останется без диагностической причины.
3. Новый частичный `DailyDecisionContext`, автоматические повторы или запрет
   советов при любом пропущенном показателе — отдельные решения со своими
   trade-offs; не входят в этот план и требуют обсуждения и ADR.

## Выполненный объём

1. Только для execution failure двух reads выдавать server-generated UUID
   в TextContent и structuredContent; фиксированный `read_failed` сохраняет
   неизвестность причины. UUID не включать в обычный ответ Coach.
2. Логировать UUID, фиксированные tool/category и SQLSTATE только из
   существующего закрытого allowlist. Не логировать input, Person, health
   values, SQL, parameters, message, stack, arbitrary cause или credentials.
   Authorization/input failures сохраняют отдельную семантику и не становятся
   runtime failure. Произвольные ошибки не выдаются клиенту.
3. Явно передавать действующее ограничение в error result и Training presenter:
   известная очередь B и частота не являются рекомендацией B сегодня;
   досып сам по себе не доказывает готовность; нормальное самочувствие нельзя
   приписать пользователю без сообщения; завтра не обещается восстановление.
   Полный отказ обязательного дневного контекста не обходится выводом готовности
   из отдельных reads или истории чата. Полезный фактический ответ сохраняется.
   Успешный частичный контекст по-прежнему позволяет осторожный совет по
   проверенным фактам, существенным ограничениям и запросу человека.
4. Проверить exception/privacy/UUID correlation, отдельные auth/input paths,
   отказ композиции и успешное последующее чтение. Добавить реальный
   MCP-to-service-to-isolated-PostgreSQL сценарий для составного Recovery read
   вместо одного готового mocked результата; данные только синтетические.
5. Провести независимую Quality, API typecheck/build/lint и релевантные tests.
   После принятия обновить только affected canonical Wiki, повторить Quality
   документации, docs validator и Architecture Review. Новый ADR не требуется
   при сохранении перечисленных границ; обнаруженное расхождение обсуждается.

## Критерии приёмки и ограничения

- Отказ имеет приватно безопасную корреляцию; код и произвольное сообщение
  исключения не принимаются за доказанную причину по умолчанию.
- Тест доказывает путь реальной композиции через MCP в изолированной базе,
  а не только соответствие текста инструкции.
- Full-context failure и отдельный missing metric различаются в инструкциях;
  расписание, досып и неизвестное самочувствие не заменяют текущие факты.
- Локальная проверка инструкций не доказывает поведение внешней модели Coach.
  Live canary и доставка возможны только после отдельного разрешения.
- Прошлая runtime-причина остаётся неизвестной, пока нет новых доказательств;
  диагностическое улучшение не объявляется исправлением причины инцидента.
- Независимая Quality и docs validation пройдены до завершения реализации.

## Результат проверки

- Два execution failure получают UUID в text/structuredContent и безопасную
  корреляцию в существующем logger. Неизвестная ошибка авторизации не
  классифицируется как выполнение чтения; invalid input/OAuth paths сохранены.
- Общие инструкции для обоих Training presenters и error result различают
  отказ дневного контекста и пропущенный показатель в успешном контексте.
  Алгоритм Recovery и исходные факты не менялись.
- Реальный MCP/CurrentRecovery/Recovery/Integration/preferences/PostgreSQL
  сценарий сохраняет две отдельные синтетические записи сна, прерывает один
  owner read, получает diagnostic ID и затем успешно читает контекст. Вывод
  не содержит Person identity, а сохранённые записи не меняются.
- Полный API unit suite: 383 tests до последнего узкого guard на execution;
  после него 13 read-error tests и API typecheck/build/targeted eslint прошли.
  Независимая Quality проверила 34 unit и все 11 MCP/PostgreSQL tests на
  финальном коде, docs validator и diff check. Все проверки прошли.
- Architecture Review подтверждает прежние owner boundaries, отсутствие
  новых сущностей/сервисов/таблиц/миграций/правил готовности и минимальный объём.
  После принятия обновлена только affected Coaching Wiki; отдельная проверка
  документации завершает локальную задачу.
- Прошлая временная runtime-причина неизвестна. Реализация устраняет
  диагностический пробел и уточняет действующие инструкции; не объявляется
  устранением неизвестной причины инцидента. Поведение внешней модели Coach
  и наличие изменений на staging не доказаны локальными tests. Live canary,
  commit/push/deploy остаются отдельными разрешениями.
