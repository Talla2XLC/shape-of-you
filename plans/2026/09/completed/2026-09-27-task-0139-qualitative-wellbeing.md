# TASK-0139 — словесное самочувствие как факт Recovery

## Цель

Однозначное сообщение о самочувствии без чисел сохраняется типизированно, а
Coach показывает пересчитанное API решение. Неясность уточняется коротко;
отчёт после каждого ответа не обязателен.

## Утверждённая архитектура

- [ADR](../../../../docs/adr/20260927-record-qualitative-wellbeing-in-recovery-and-reassess.md):
  отдельная качественная форма внутри `RecoveryObservation.subjective`, новая
  версия `Daily Assessment`, только консервативное влияние на нагрузку.
- Полный числовой check-in и старые snapshots остаются читаемыми. Никаких
  придуманных шкал, неявных `false`, изменений TrainingProgram и записи в
  окружение.

## Шаги

1. Зафиксировать аналитический handoff и developer plan в board.
2. Добавить строгий контракт и миграцию двух форм subjective detail,
   проверить идентификаторы PostgreSQL на предел 63 UTF-8 bytes.
3. Сохранить create/retry/correct/read-back через Recovery; исключить
   qualitative из числового Recovery scorer.
4. Добавить Daily Assessment v6 с точными сигналами в usedFacts и checksum;
   negative signals только ограничивают решение.
5. Обновить MCP policy: ясный текущий отчёт записать и пересчитать, при
   существенной неясности уточнить, без навязчивого check-in.
6. Добавить unit, contract, PostgreSQL integration и MCP policy тесты;
   выполнить независимый Quality Review, Architecture Review, Wiki alignment.

## Критерии приёмки

- «Сегодня устал» записывается без чисел и переводит достаточно обоснованное
  решение в осторожное; при нехватке данных она сохраняется. «Болею» или
  опасение травмы дают recovery hard stop.
- «Чувствую себя хорошо» не отменяет существующий hard stop и не создаёт
  ready при нехватке данных.
- Несвязанный текст не вызывает write/assessment; неясная дата или смысл
  вызывает только нужное короткое уточнение.
- Исправление наблюдения меняет новый API read, а старые снимки остаются
  воспроизводимыми. Полный check-in не теряет контракт.
- Нет коммита, push, deploy или исполнения миграции в окружении без
  отдельного разрешения.

## Результат

- Контракт и две миграции разделяют полный числовой и качественный факт.
  `Daily Assessment` v6 сохраняет точные сигналы в снимке и checksum.
- Coach policy записывает однозначный текущий факт, читает его обратно и
  получает пересчитанное решение API; неясность уточняет без обязательного
  отчёта после каждого ответа.
- Независимый Quality Review принял TASK-0139 после исправления приоритета
  `insufficient_data`, тестов SQL CHECK и старого v5 снимка, а также
  изоляции интеграционных сценариев. Unit: 306; PostgreSQL Recovery: 19;
  Daily Assessment: 10; миграционные: 19. TypeScript, lint и валидатор
  документации прошли.
- Изменения остались локальными в основном рабочем дереве. Миграции
  подготовлены и проверены в изолированном PostgreSQL; они не применялись
  к staging или production. Коммита, push и deploy этой задачи нет.

## Architecture Review

1. Дополнительной сущности или второй модели самочувствия нет; используется
   владеющий Recovery и существующий жизненный цикл исправлений.
2. Нового сервиса, базы или границы развёртывания нет.
3. Recovery владеет фактом, Coaching — решением; действующая TrainingProgram
   не меняется. Отрицательный сигнал не обходит Daily Assessment.
4. ADR хранит решение и альтернативы, Wiki — только текущие правила,
   план — проверенное исполнение.
5. Две формы одного типизированного detail и консервативная надстройка v6 —
   самый простой вариант без потери истории и воспроизводимости.
