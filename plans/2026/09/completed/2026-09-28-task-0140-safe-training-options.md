# TASK-0140 — выбор допустимого тренировочного действия

## Цель

Дать Coach выбрать разумное действие по контексту, сохранив точную очередь
Ahilej A/B, недельные цели и приоритет Recovery. Не навязывать кардио после
силовой только из-за порядка событий.

## Утверждённое решение

- [ADR](../../../../../docs/adr/20260928-let-coach-choose-safe-training-options.md):
  Training отдаёт проверенные допустимые варианты; Daily Assessment применяет
  safety gate; Coach выбирает и объясняет один вариант только при `ready`.
- Старые snapshots остаются читаемыми. Калибровка пульсовых зон не входит в
  задачу. Нет migration, runtime data write, commit, push или deploy.

## Шаги

1. Изменить versioned `NextTrainingStep` contract и чистую Training проекцию:
   отделить A/B identity и недельные квоты от выбора вида занятия.
2. Обновить Daily Assessment, completion semantics и MCP-инструкции так,
   чтобы агент выбирал только допустимый вариант после Recovery gate.
3. Добавить unit и PostgreSQL tests для перехода недели, закрытой нормы кардио,
   пропущенных дней, ambiguity, Recovery hard stop и исторических snapshots.
4. Выполнить проверки, независимый Quality Review, затем обновить только
   затронутые current-state Wiki страницы и провести Architecture Review.

## Критерии приёмки

- После A 25 сентября следующий strength identity — B; на 28 сентября
  кардио не становится обязательным только из-за смены недели.
- Когда обе недельные цели не закрыты, оба проверенных варианта доступны.
  Когда кардио выполнено дважды, оно больше не предлагается как цель недели.
- Пропуск дней не продвигает A/B и не накапливает долг кардио.
- Recovery `hard stop` не даёт тренировочного совета даже при доступных
  вариантах; без надёжной A/B identity агент её не угадывает.
- При двух вариантах completion не угадывает, какой из них выбрал Coach:
  нужен ответ человека. При одном варианте проверяется точная силовая позиция
  или подходящее несвязанное кардио.
- Нет изменения зон пульса, active program, staging/prod данных или миграции.

## Результат

- `training-next-step-v4` отдаёт допустимые варианты и недельный progress.
  После Ahilej A 25 сентября следующая силовая — B; кардио не навязывается
  через понедельник или пропущенную неделю.
- Daily Assessment сначала применяет Recovery. MCP Coach выбирает один
  проверенный вариант только при `ready` и объясняет выбор по контексту.
- Completion для двух вариантов требует подтверждения человека, поскольку
  разговорный выбор не хранится в snapshot. Единственный вариант проверяется
  по точной силовой позиции либо qualifying uncovered cardio.
- Независимый Quality Review принят. Перед итоговой записью прошли 67
  затронутых unit tests, 14 PostgreSQL Training integration tests, contracts
  build, API typecheck/lint/build, docs validator и `git diff --check`.
  После финальных правок полный API-набор: 53 файла, 421 тест успешно.
- Активная программа, staging/prod данные и пульсовые зоны не менялись;
  миграций, commit, push и deploy не было.

## Architecture Review

1. Сложность ограничена новой закрытой union-веткой и точным completion.
   Сохранённого cursor, общего rules engine и произвольного threshold нет.
2. Новый микросервис, database, queue и deployable boundary не добавлены.
3. DDD сохранён: Training владеет A/B identity и недельными facts, Recovery —
   safety signals, Coaching — итоговым разрешением и Coach — разговорным
   выбором только среди допустимых вариантов.
4. ADR содержит решение, Wiki кратко описывает действующий контракт, план
   фиксирует выполнение; второй источник тренировочных фактов не создан.
5. Существующие read и immutable snapshots повторно используются.
   Упрощение до единственного hard-coded шага теряет требуемую свободу после
   паузы; дальнейшее усложнение с сохранением conversational choice пока не
   оправдано. Его отсутствие явно выражено в completion semantics.
