# Перевод проектной документации на русский язык

## Цель

Сделать русский язык единым языком планов, canonical Wiki, ADR и руководств
Shape of You, сохранив стабильность ссылок, идентификаторов и машинной
валидации.

## Принятое направление

- Планы, Wiki, ADR и руководства создаются и поддерживаются на русском языке.
- Общепринятые технические термины, имена сущностей, API, типов, команд и
  продуктов могут оставаться на английском, когда перевод ухудшает точность.
- Managed Wiki в SQLite не используется и не изменяется.
- Git commit не создаётся.

## Сравнение вариантов

### A. Перевести только основной текст

Оставить английские названия разделов, titles и шаблоны.

Плюсы:

- минимальный diff;
- validator почти не меняется.

Минусы:

- смешанный язык остаётся частью ежедневного workflow;
- новые документы будут выглядеть непоследовательно;
- требование «Wiki и ADR на русском» выполняется не полностью.

### B. Перевести весь человекочитаемый слой

Перевести titles, заголовки, разделы, таблицы, основной текст, templates и
руководства. Сохранить пути файлов, `id`, YAML-ключи и служебные enum.

Плюсы:

- единый язык для команды;
- ссылки и история файлов остаются стабильными;
- машинный контракт остаётся предсказуемым;
- не требуется массовое переименование и переписывание ссылок.

Минусы:

- большой одноразовый diff;
- validator нужно атомарно перевести на новые обязательные разделы.

### C. Перевести также пути и идентификаторы

Переименовать файлы, каталоги, `id`, enum и metadata keys.

Плюсы:

- максимальная локализация.

Минусы:

- ломаются ссылки и внешние указатели;
- ухудшается Git history/blame;
- возрастают миграционные риски;
- технические metadata становятся менее совместимыми с инструментами.

## Решение для выполнения

Использовать вариант B.

Стабильными остаются:

- пути и имена файлов;
- `id`;
- YAML-ключи;
- `kind`, `status` и их значения;
- даты;
- имена технологий, команд, API и domain concepts, когда они являются частью
  технического контракта.

Переводятся:

- `title`;
- заголовок `#`;
- обязательные заголовки разделов;
- основной текст;
- подписи таблиц и списков;
- тексты templates;
- language policy в `AGENTS.md`;
- руководство `docs/README.md`;
- человекочитаемые сообщения validator.

## Каноническая структура разделов

### Структура Wiki

1. `## Кратко`
2. `## Содержание`
3. `## Основания`
4. `## Решения`
5. `## Открытые вопросы`
6. `## Связанные материалы`

### Структура ADR

1. `## Контекст`
2. `## Решение`
3. `## Рассмотренные альтернативы`
4. `## Последствия`
5. `## Проверка`
6. `## Связанные материалы`

## Объём

- 23 страницы `docs/wiki/`;
- 12 ADR в `docs/adr/`;
- `docs/templates/wiki-page.md`;
- `docs/templates/adr.md`;
- `docs/README.md`;
- language policy в `AGENTS.md`;
- связанные пояснения в root `README.md`;
- `scripts/validate-docs.ps1`;
- проверка уже существующих планов и руководств на противоречащие language
  rules.

## Порядок выполнения

1. Обновить language policy в `AGENTS.md`.
2. Обновить canonical templates и validator одним атомарным этапом.
3. Перевести Wiki по областям:
   - start, vision, product, roadmap и changelog;
   - architecture;
   - data;
   - domain.
4. Перевести ADR без изменения смысла решений.
5. Обновить documentation guide и root README.
6. Проверить все относительные ссылки.
7. Найти остаточные английские policy statements и непреднамеренно
   непереведённые фрагменты.
8. Запустить validator из корня и из другой текущей директории.
9. Выполнить Architecture Review.
10. После принятия перенести план в `completed/`.

## Правила перевода

- Не менять архитектурный смысл.
- Не добавлять новые решения во время перевода.
- Не переводить имена сущностей так, чтобы возник новый ubiquitous language
  без отдельного обсуждения.
- Не менять статус документа.
- Не создавать дубликаты страниц.
- Сохранять относительные ссылки и anchors либо обновлять их атомарно.
- Не использовать машинный перевод без содержательной проверки.

## Критерии приёмки

- Language policy требует русский для планов, Wiki, ADR и руководств.
- Все 35 canonical документов имеют русский человекочитаемый слой.
- Templates создают документы с русскими разделами.
- Validator проверяет русские обязательные разделы и выдаёт понятные сообщения.
- Все IDs, пути и служебные enum сохранены.
- Все относительные ссылки работают.
- Managed Wiki, source registry и installed 4DreamTeam не изменены.
- Architecture Review выполнен.
- Git commit не создан.

## Риски

- Перевод может незаметно изменить смысл принятого ADR.
- Массовый diff усложняет review.
- Неоднозначный перевод domain terms может преждевременно закрепить
  ubiquitous language.
- Одновременное существование английских templates и русских страниц создаст
  смешанный формат, поэтому templates и validator меняются атомарно.

## Стратегия проверки

- Сравнить количество файлов и IDs до и после.
- Проверить `kind` и `status`.
- Проверить обязательные разделы.
- Запустить link validation.
- Точечно сопоставить каждый ADR с исходным решением.
- Использовать `rg` для поиска старых language-policy statements и типовых
  английских заголовков.

## Architecture Review до выполнения

1. **Избыточная сложность:** переводится только человекочитаемый слой;
   переименование файлов и metadata отклонено.
2. **Микросервисность:** runtime и deployable boundaries не затрагиваются.
3. **DDD:** перевод не должен менять bounded contexts, aggregates, invariants
   или ubiquitous language без отдельного решения.
4. **Дублирование:** новые копии документов не создаются; существующие
   canonical файлы обновляются на месте.
5. **Упрощение:** вариант B даёт единый язык без миграции идентификаторов и
   ссылок и является минимальным полным выполнением требования.

## Результат

- Переведён человекочитаемый слой 23 страниц canonical Wiki и 12 ADR.
- Переведены `AGENTS.md`, root `README.md`, `docs/README.md`, templates и
  сообщения validator.
- Сохранены пути, имена файлов, 35 уникальных `id`, YAML-ключи, `kind`,
  `status`, даты и технические contract terms.
- Исправлены относительные ссылки, перенесённые из прежней структуры managed
  Wiki.
- ADR о canonical Markdown приведён в соответствие уже принятому решению:
  managed Wiki остаётся frozen legacy copy и не подлежит очистке без отдельного
  явного решения.
- Validator успешно выполнен из корня репозитория и из внешней текущей
  директории: 23 страницы Wiki, 12 ADR, 35 уникальных `id`.
- `.4dt/db.sqlite3`, source registry и 4DreamTeam не изменялись; каталог
  `.4dt/backups` отсутствует; `docs/` не зарегистрирован в sources.
- Git commit не создавался.

## Architecture Review после выполнения

1. **Избыточная сложность:** новая инфраструктура не добавлена. Изменены только
   canonical документы, templates, workspace guide и существующий validator.
2. **Преждевременная микросервисность:** runtime, deployable units и сервисные
   границы не создавались и не изменялись.
3. **Domain-Driven Design:** сохранены пять draft bounded contexts, независимые
   факты вместо широкого `DayRecord` и технические элементы ubiquitous
   language. Перевод не создаёт новых доменных сущностей.
4. **Дублирование:** Wiki хранит текущее состояние, ADR — решения и
   компромиссы, план — ход и проверку миграции. Новые копии документации не
   создавались.
5. **Упрощение:** сохранение стабильных путей, IDs и metadata исключило
   миграцию ссылок и интеграций. Более простого варианта, полностью
   обеспечивающего единый русский человекочитаемый слой, не обнаружено.

Architecture Review не выявил оснований менять утверждённую архитектуру.

## Состояние

Завершено. Русский человекочитаемый слой применён при стабильных путях, IDs и
технических metadata.
