# TASK-0178 — Единое подтверждение результатов MCP

Статус: локальная реализация принята независимой Quality 2026-11-15,
`task0178-local-quality`. Объём утверждён оператором сообщением «го» после
проверки всех 24 операций записи, включая compatibility commands.
Коммит, push и доставка не выполнялись.

## Основание и границы

Применяются принятые ADR `20261009-let-coach-propose-working-weight-from-history`
и `20260902-evolve-mcp-tool-schemas-backward-compatibly`: достоверные результаты,
проверка неопределённого исхода до повтора, совместимость существующих inputs.
Это исправление выполнения существующих контрактов, а не новая архитектура.
Новых сущностей, сервисов, хранилищ, миграций и физиологических правил нет.

Сравнение вариантов: отдельные исключения для каждого инструмента уже привели
к пропускам; общий MCP adapter устраняет эту причину. Выбран общий сериализатор
результата и проверка схем записей при сохранении предметных правил проверки
состояния и повтора. Обязательное чтение после каждого успешного ответа лишнее:
валидный canonical result уже подтверждает запись.

## Утверждённый план

1. Передавать одинаковые canonical данные в `structuredContent` и JSON TextContent
   во всех успешных чтениях и записях, сохраняя действующие инструкции.
2. Объявить существующие output schemas у оставшихся 11 операций записи.
   Централизованно проверять результаты всех записей; пустой или неверный результат
   не должен порождать ложное подтверждение сохранения.
3. Различать известное отклонение и неизвестный исход исполнения/подготовки ответа.
   Исправить `not_saved` при неопределённом сохранении программы и cadence.
   Для остальных операций дать конкретный путь чтения без слепого повтора:
   сохранить identity, исходный ключ, параметры, версии и несвязанные изменения.
   Не вызывать повторные записи сервером автоматически.
4. Проверить каталог и обе формы результата, защиту от пустого/неверного ответа,
   сбои до записи и после сохранения, сбои представления, недоступное чтение,
   известные отклонения и exact retry без дублей на синтетических данных.
5. Выполнить API typecheck/build, применимые unit/integration checks, independent
   Quality, Architecture Review и сверку ADR/Wiki. После приёмки обновить только
   затронутые Wiki страницы и перенести план в `completed/`.

## Критерии приёмки

- У всех записей есть output schema; invalid result не считается success.
- Все успешные tool results доступны клиенту без поддержки structuredContent.
- Произвольная ошибка после начала исполнения не доказывает отсутствие записи.
- Неопределённый исход требует проверки current state; не допускает слепой retry,
  новый dedupeKey или перезапись чужих изменений.
- Сохраняются authorization, Person ownership, immutable corrections, concurrency,
  inputs и отсутствие обязательного чтения после валидного success.
- Реальные пользовательские записи, сеть, staging и production не используются.

Коммит, staging, push, deploy и доступ к реальным данным не разрешены этим планом.
Восемь ранее существовавших изменений рабочего дерева исключены из объёма.
Причина исходного клиентского сбоя без trace остаётся недоказанной.

## Результат и проверки

- Общий adapter передаёт canonical JSON всех успешных чтений/записей и
  структурированных ошибок. Все 24 записи имеют output schema и проверку
  результата до подтверждения успеха; 11 недостающих схем добавлены.
- Неопределённый результат записи или подготовки ответа обозначается `unknown`,
  включая program/cadence. Проверка факта использует действительные параметры
  чтения; Weight/Body используют pagination без несуществующего `localDate` input.
- Независимая проверка выявила несовместимость дробных `multipleOf` и повторных
  вложенных `$id` со стандартным MCP SDK. Общая публикация output schemas теперь
  устраняет эти ограничения только в копии для клиента; строгая серверная
  проверка и исходные schemas сохранены. Каталог после JSON round-trip
  компилируется одним SDK validator; дробный Meal проходит настоящий SDK.
- Закрыто ложное подтверждение `stale` в title, recording mode и workout link.
  Предметные outcomes сохранены; неподтверждённое изменение не выдаётся за запись.
- Финальные проверки: API unit 448/448; isolated PostgreSQL 20/20
  (Meal/Weight 7 и Training flow 13); typecheck/build, scoped ESLint и diff check
  прошли. Тесты включают потерю подтверждения до/после commit, точный replay без
  дублей, failed read, неверный/пустой output и presentation failure.
- Docker socket недоступен. Использован собственный временный native PostgreSQL
  на `127.0.0.1:55478` в `/private/tmp/soy-task0178-pg`. Миграции выполнял test
  harness только в двух изолированных синтетических базах; новых миграций нет.
  Staging/production и пользовательские данные не использовались.
- Независимая Quality проверила каждый критерий, повторила 35 focused unit,
  typecheck и 20 PostgreSQL checks; полные финальные проверки Lead отмечены
  отдельно в timeline. После приёмки обновлены две затронутые canonical Wiki pages.

## Architecture Review

1. Общий adapter проще отдельных исключений; используются существующие schemas,
   без новой orchestration сущности или автоматического повторного writer.
2. Новых сервисов и deployable boundaries нет.
3. Владельцы доменов, Person scope, immutable corrections, concurrency и dedupe
   сохранены; Coach интерпретирует факты в рамках принятого ADR.
4. Общий контракт описан в одной Wiki странице; Meal ссылается на неё. План хранит
   выполнение, а действующие ADR сохраняют архитектурную authority.
5. Кеш валидаторов устраняет повторную компиляцию write schemas; API boundary
   остаётся прежней. Более простого решения с теми же гарантиями не обнаружено.

Новый ADR не требуется: новых решений о модели, ownership или topology нет,
исправлено выполнение уже принятых решений. Поведение исходного клиентского
диалога не проверено; успешные синтетические тесты не доказывают его исправление
до отдельной разрешённой доставки и клиентской проверки.
