# TASK-0177 — Проверять неопределённый результат исправления Meal

Статус: локальная реализация и дополнение приняты независимой Quality
2026-11-13. Доставка не выполнялась.

## Проблема и границы

При расследовании обращения текущая запись уже содержала исправление, хотя
Coach сообщил об отсутствии подтверждения. Повторная запись не выполнялась.
Причина первоначального неопределённого ответа без trace вызова неизвестна.
Персональные данные обращения в план не включаются.

В `apps/api/src/mcp/server.ts` общий catch для `correct_meal` вызывает
`mealCorrectionErrorResult("retryable_failure")`. До исправления ответ маркировал результат
как `not_saved` и предлагает повтор вместо первичной проверки текущей записи.
Это не доказывает причину обращения, но является воспроизводимым дефектом
контракта неопределённого результата. Успешный canonical result, напротив,
должен подтверждать запись без обязательного повторного чтения.

Архитектурное основание — принятый ADR
`docs/adr/20261009-let-coach-propose-working-weight-from-history.md`.
Новых сущностей, сервисов, миграций и изменений физиологических правил нет.

## Утверждённый объём

1. Различить известный отказ и неизвестный результат записи в MCP ошибках Meal.
   Не обозначать произвольное исключение как доказанное отсутствие сохранения.
2. При неизвестном результате предписывать чтение текущей Meal за нужную дату
   и сравнение полного принятого исправления. Совпадение подтверждает сохранение;
   неизменённый predecessor допускает точный идемпотентный повтор; конкурирующее
   изменение требует сохранения чужих полей. Недоступное чтение сохраняет unknown.
3. Сохранить достаточность успешного canonical result и запрет повторно применять
   уже успешную поправку. Уточнять только материальную неоднозначность исходных
   фактов, включая сырой/готовый вес, не требовать повторного разрешения записи.
4. Добавить MCP unit и isolated PostgreSQL проверки потери подтверждения после
   commit, неопределённой ошибки до commit, повторов, конфликтов и failed read.
   Проверить состав и количества неизменённых Meal items.
5. Провести независимую Quality, сверку с ADR/Wiki и обновление только затронутой
   текущей документации после приёмки; API typecheck/build, применимые тесты,
   `node scripts/validate-docs.mjs`. После реализации перенести план в completed.

## Критерии приёмки

- Сбой ответа не превращается автоматически в `not_saved`.
- Сохранённая поправка подтверждается чтением, без дубля и повторного correction.
- Неизвестность остаётся явной, если исход записи проверить нельзя.
- Успешная запись не получает обязательного дополнительного чтения.
- Ownership, immutable corrections, dedupe и optimistic conflicts сохраняются.
- Оценочные количества не выдаются за измеренные; масса остаётся в исходном
  состоянии приготовления либо явно оговаривается предположение.

Коммит, push, deploy, доступ по SSH и реальные записи пользователя этим планом
не разрешаются. Точная причина исходного сбоя остаётся неизвестной до получения
результата вызова или безопасной корреляции диагностики.

## Результат локальной реализации

- `list_meals` требует сначала сравнить текущую запись с принятым исправлением;
  совпадение подтверждает сохранение без нового correction. Неизменённая исходная
  запись допускает точный повтор; чужие параллельные изменения сохраняются.
- Успешный canonical result достаточен; недоступное проверочное чтение сохраняет
  unknown. Добавлено требование не подменять неизвестный сырой/готовый вес.

- Причина исходного сбоя остаётся неизвестной без trace. Запись пользователя
  не изменялась. Коммит, push и доставка этого исправления не выполнялись.
- Независимая Quality: task-0177-local-quality-20261113. Проверены критерии

## Дополнение: пустой результат успешного вызова

Оператор передал ответ Coach: видимый результат предыдущего `correct_meal` —
`{}`, без success/error. Это свидетельство видимого клиентом результата,
не сырой wire trace и не доказательство места потери данных. Текущая запись
ранее подтверждена отдельным read; повторные пользовательские записи не нужны.

До дополнения `correct_meal` использовал `outputSchema = undefined`.
`successResult` сохранял canonical Meal в `structuredContent`, но при заданном
presentation возвращал в `content` только guidance без JSON факта. Спецификация
MCP рекомендует сериализованный JSON в TextContent для обратной совместимости:
https://modelcontextprotocol.io/specification/2025-06-18/server/tools

Дополнение утверждено оператором сообщением «go» и реализовано:

1. Объявить существующую Meal output schema для `correct_meal`, не меняя input,
   доменную модель, права, endpoint или persistence. Проверить совместимость
   успешных и error результатов с MCP SDK.
2. Дублировать canonical Meal успешной коррекции в отдельном JSON TextContent
   блоке вместе с прежним guidance, не меняя остальные инструменты без основания.
3. Проверить discovery, равенство structured и текстового результата, parsing
   клиентом без structuredContent, error-state различия и реальные synthetic
   PostgreSQL результаты. Отдельно проверить уже действующую серверную схему.
4. Повторить независимую Quality; после разрешённой доставки обновить клиентский
   каталог и проверить синтетический ответ. Не выдавать устранение этой уязвимости
   за доказанную причину исходного `{}` без исходной трассировки.
